# Media resource governance: integration and limitations

## Current state

The existing Compose configuration runs media work inside `backend`; JDownloader runs in a separate container. Its CPU-thread and RAM-ratio settings are sizing hints, not cgroup controls. They do not reserve a core, enforce an aggregate budget, or guarantee free host RAM. `backend/resource_governance.py` adds a read-only diagnostic and conservative admission interface; it is **not wired into any workload** and does not create, modify, or enforce cgroups. Strict admission intentionally stays denied until comprehensive workload coverage is implemented and verified. No provisioning script was installed or executed.

## Intended Linux architecture

On Ubuntu 24.04 with systemd and unified cgroup v2, a separately provisioned systemd slice, for example `media-pipeline.slice`, must have finite `CPUQuota` and `MemoryMax` on the **shared parent**, not merely per-process thread limits or independent container limits. CPU quota is a time budget, not a dedicated physical core; competing workloads and CPU affinity still affect throughput. A memory cap is not a guarantee that the remainder of RAM is free: the kernel, services, page cache, and other workloads also consume memory. Memory accounting includes charged page cache and shared memory; hitting the cap can trigger cgroup OOM kills. Choose explicit CPU and byte limits after reviewing host and ancestor constraints; do not derive a guarantee from the 90% configuration ratio.

For complete coverage, an implementation needs all of the following before claiming enforcement:

1. Run *all* media work in dedicated media worker container(s) or supervisors under this shared slice, separate from the backend API, MongoDB, and other nonmedia services. Current backend launches media work, so merely placing `backend` under the slice also caps the API and is not this isolation. A worker must enter the slice **before** it can start work; attaching a running parent does not move already-existing descendants. Children inherit membership unless a privileged process moves them elsewhere. No out-of-band launch route may bypass the admission gate.
2. Configure JDownloader's entire container under the same shared slice with a reviewed Compose override using Docker's systemd `cgroup_parent` (for example, `media-pipeline.slice` when the daemon uses the systemd cgroup driver). Do not set that parent on the existing backend to simulate worker isolation. Confirm the actual host cgroup hierarchy and all container init processes after startup; driver and cgroup namespaces matter. Persistent configuration should preserve existing settings and be reviewed by the owner.
3. Stop and reconcile old media processes before cutover; inventory every media worker and its descendants as well as JDownloader container init and its descendants. Ensure no other worker instance, subprocess, or container runs outside the slice. Establish a trusted, race-safe inventory and prevent escape or unauthorized migration. Periodically and on every restart revalidate membership, caps, and process identity; PID reuse, process exit, container replacement, and movement can invalidate a snapshot. Cgroup membership at a single instant alone does not prove future or exhaustive coverage.
4. Fail closed before enqueueing/launching work, including all downloader, FFmpeg, subtitle/Whisper and other subprocess paths, when verification or inventory is unavailable. Require the shared limit and all required controllers; check enclosing ancestor quotas and cgroup namespace visibility. Avoid granting workloads permission to modify their own or parent cgroups. Establish a controlled response if coverage becomes invalid after admission.

There is currently no implementation of these coverage and placement requirements. In particular, passing a list of named PIDs to the diagnostic is not proof that the list is complete. Until a future owner-reviewed implementation supplies this architecture and complete verification, do not switch the strict gate to allow admission and do not report governance as active.

## Diagnostic API

Call `assess_admission(group, worker_pids, jdownloader_init_pid, max_cpu_cores, max_memory_bytes, *, strict=True)` from `backend.resource_governance`. `group` is the absolute path of the shared non-root cgroup; use host-visible positive integer PIDs for worker supervisors and JDownloader container init. Both explicit caps must be positive (`max_memory_bytes` is an integer). This is read-only and must run with host PID and host cgroup namespaces and permission to inspect the complete hierarchy. A container-private cgroup namespace can hide tighter ancestors and makes diagnostics incomplete; the function cannot automatically prove host namespace visibility.

The returned immutable `GovernanceStatus` has `supported`, `admission_allowed`, `enforcement_active`, `reason`, `group`, `effective_cpu_cores`, `effective_memory_bytes`, `cpuset_cpus_effective`, and `checked_pids`. The CPU value is the smallest visible ancestor `cpu.max` ratio, an upper bound in core-equivalents, **not** physical-core allocation or guaranteed capacity; cpusets and other contention may restrict it further. The memory value is the smallest visible `memory.max` byte limit, not available/free memory. An ancestor shared with unrelated workloads can make less capacity available to media. `supported=True` means named anchors and visible finite caps were checked, not that all media is covered. Strict mode always returns `admission_allowed=False` and `enforcement_active=False` at this stage. `strict=False` explicitly permits operation without verified enforcement; never use it to label governance active. Missing controllers, invalid files, unsupported platforms, incorrect PIDs, and inaccessible hierarchy result in unsupported status and strict denial.

The verifier requires a finite limit on the shared media group itself, even if a higher ancestor is finite, and requires each named PID to appear in the group or a descendant. The diagnostic reports a snapshot and cannot itself prevent process migration, verify PID identity over time, or establish complete coverage. It also cannot prove the caller supplied the host namespaces. Do not expose it as a security boundary on its own.
